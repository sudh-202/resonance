# AI Workflow Rules

## Approach

Use these context files as the operating baseline for LLM work in this repo. They describe the current Resonance TTS platform, stack, styling, architecture, feature-level specs, and implementation rules. Before changing product behavior, read the relevant context file, then verify against live source files because this project is actively evolving.

## Required First Reads

For any non-trivial implementation, read:

1. `context/project-overview.md`
2. `context/architecture.md`
3. `context/ui-context.md`
4. `context/code-standards.md`
5. `context/progress-tracker.md`

Then read the matching file in `context/feature-specs/` if one exists for the feature area. After that, read the owning source files. Do not implement from the context docs alone — always verify current source.

If the task involves background audio processing, long-running generation jobs, scheduled tasks, durable workflows, or AI agent orchestration, also read `context/external-skills.md`.

## Scoping Rules

- Work on one feature unit at a time (e.g., voice library OR TTS studio, not both).
- Never mix voice data changes, studio UI changes, R2 storage changes, and auth changes in a single patch.
- Keep the Clerk `orgId` tenancy boundary intact in every change that touches Voice or Generation data.
- Treat `context/feature-specs/` files as the source of truth for feature requirements. If a spec is stale or missing, update it before implementing.
- Trigger.dev and Liveblocks are not part of the current runtime. Read `context/external-skills.md` before introducing them.
- Do not add dependencies without updating `context/architecture.md` and the relevant feature spec.

## When to Split Work

Split an implementation step if it combines:

- Voice library UI with database schema changes.
- TTS studio with R2 upload/download wiring.
- Auth/session changes with domain feature changes.
- shadcn component additions with route logic.
- A broad visual redesign with route handler logic.

If the change cannot be verified quickly through the affected page or a test command, the scope is too broad.

## Handling Missing Requirements

- Do not invent product behavior when requirements are ambiguous.
- If the ambiguity is about current behavior, read the source first.
- If it is a product decision code cannot answer, add it to `progress-tracker.md` under Open Questions before proceeding.
- If a feature changes architecture, styling, storage model, routes, or product scope, update the relevant context file in the same task.

## Protected Areas

Do not modify the following unless explicitly instructed:

- `node_modules/`
- `.next/`
- `src/generated/prisma/` — auto-generated by `prisma generate`
- Lock files unless dependency changes are part of the task

## Command Rules

- Prefix shell commands with `rtk` in this workspace.
- Use `rg` / `rg --files` for searching where possible.
- Run `next build` to verify compilation; run `next dev` to check runtime behavior.
- After Prisma schema changes: `prisma migrate dev` (or `prisma db push` for rapid iteration), then `prisma generate`.
- Use `npx shadcn@latest add <component>` to install new shadcn/ui components.

## Keeping Docs in Sync

Update context docs when any of these change:

- Framework, package, or rendering strategy.
- CSS variable tokens, theme, fonts, or component library.
- Core routes or feature ownership boundaries.
- Database schema or R2 storage conventions.
- Auth model or Clerk org-scoping rules.
- Product direction or major user flows.
- External integration status (Trigger.dev, Liveblocks, TTS provider).
- Feature-specific implementation requirements in `context/feature-specs/`.

## Before Moving to the Next Unit

1. The affected route/component works within the defined scope.
2. The Clerk `orgId` check is present on every new route handler that touches org-scoped data.
3. No invariant in `context/architecture.md` was violated.
4. `context/progress-tracker.md` reflects the completed work or open questions.
5. A relevant verification command or manual check has been run, or the reason for skipping is recorded.
